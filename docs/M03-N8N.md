## How the workflow behaves

`Run manually → Proposed lead → Ask AgentAxio (POST /v1/action-requests) → Accepted? → wait 5 s → Check status (GET) → Finished? → report`.

- The only secret in n8n is the AgentAxio agent key, in a Header Auth credential. The workflow file contains none, and no CRM node or CRM credential exists in it.
- The `Idempotency-Key` is computed once in `Proposed lead` (n8n's `$execution.id` is only a placeholder in manual test runs, so it is not used). The request step may retry up to 3 times; every retry sends the same key, so it can never create a second request. A new run gets a new key and needs its own approval.
- Only HTTP 202 continues. `403 denied` ends with a "not created" report. Anything else (including AgentAxio being unreachable, or a revoked key or suspended agent during polling) stops the workflow with an error: it fails closed.
- Polling is bounded (180 checks × 5 s ≈ 15 minutes, the approval lifetime). Giving up is reported as *still waiting, not a failure*, never as success.
- Only the status `succeeded` is reported as the lead being created; `unknown` tells the person not to retry blindly.

## What is verified

- **Contract tests (in CI, `n8n.test.ts`, 18):** golden path with n8n-shaped headers; allow path; deny and default-deny answers; six parallel retries with one key → one request, one approval, one lead; changed payload under a used key → 409; revoked key → 401 on poll and submit, waiting request never runs; suspended agent → 403 and withdrawn; another workflow's key → identical 404; wrong/missing key → 401 and nothing created; identity-bearing or extra fields → 422; the agent key is useless at the CRM (401); workflow file has no secrets, no CRM node, stable key, bounded polling, fail-closed branches.
- **Real n8n 2.44.7 (manual, 17/17 checks):** the shipped workflow imported into a real n8n and run with its CLI against the real stack: waits for a person; the agent's owner is refused; a different person approves; the executor creates exactly one lead in the mock CRM; n8n reports `succeeded`. A deny rule ends with "denied" and creates nothing. AgentAxio unreachable and a revoked key both make the workflow fail with nothing created.
- Web: component tests (with accessibility checks) for the connection card, setup and test guidance; unit tests for the connection logic.

## Not verified / limits (read this)

- The real-n8n run used n8n's command line in a separate folder on this machine, not the n8n editor in a browser, not n8n Cloud, and not a long-running n8n server. The workflow uses only core nodes (manual trigger, Set, HTTP Request, IF, Wait, Stop and Error), so the editor path is expected to behave the same, but that was not observed. The real-n8n script is not in CI.
- "Receiving requests" on the Integrations page means a request arrived with an agent's key; AgentAxio cannot tell n8n from any other caller and does not check workflow health.
- AgentAxio controls only requests that go through it. A workflow that keeps direct credentials to a tool can bypass it; this is stated in the product and must not be claimed otherwise.
- The only action is `crm.lead.create` and the only destination is the **mock** CRM. No production tool is connected.
- n8n must be able to reach the agent API address; the agent API listens on loopback by default. Exposing it beyond the machine (TLS, reverse proxy, trusted-proxy setting for rate limits) is a deployment decision not made here.
- n8n's own execution history stores the lead values it proposed (it proposed them, so it knows them). AgentAxio cannot control that retention.
